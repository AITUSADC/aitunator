# История экспериментов поиска

Исторические замеры до выделения поисковой части; упоминания старого чата относятся к архивному прототипу.

### Сравнение поиска без LLM

Версионируемый стенд находится в `eval/`. Он использует тот же модуль
получения кандидатов и ранжирования, что и приложение. Сравниваются `bm25`,
`dense`, `hybrid` (RRF) и `hybrid_rerank` на одном наборе из 139 вопросов.
У 92 вопросов дополнительно размечены конкретные разделы документов.

Запуск из корня репозитория после установки зависимостей:

```powershell
uv run python -m eval.run --modes bm25
uv run python -m eval.run --download-models
uv run python -m unittest discover -s tests -v
```

Первый запуск всех режимов требует загрузки BGE-M3 и bge-reranker-v2-m3.
Без `--download-models` разрешены только локальные модели. Если модель
недоступна, стенд записывает частичный отчёт и завершается с кодом 2;
`--allow-partial` явно разрешает такой результат. По умолчанию используются
CPU, 4 потока, 20 кандидатов, top-5, 3 повтора, перемешанный порядок режимов.
Reranker получает чанки с ограничением 512 токенов и batch size 8.

Результаты: `runtime/retrieval-benchmark/summary.json` и `runs.jsonl`.
В них сохраняются параметры, хеши корпуса и набора вопросов, отдельные
времена BM25/эмбеддинга/dense/rerank, исходные scores и ошибки каждого режима.
Время загрузки и прогрева отделено от замеров; кеш результатов поиска отключён.
Старые metadata boosts выключены для чистого сравнения методов; отдельный
прогон с `--metadata-boost` позволяет оценить их влияние.

Как читать метрики:

- `hit_at_5`: найден хотя бы один допустимый файл.
- `all_evidence_at_5`: найдены все обязательные группы источников; для сравнения
  двух программ нужны оба профиля, альтернативные файлы внутри группы взаимозаменяемы.
- `section_evidence_at_5`: найдены все размеченные разделы; считается только
  на вопросах с разметкой разделов. Попадание в файл с другим разделом не засчитывается.
- Вопросы без ответа исключены из retrieval-метрик. Их scores сохраняются для
  будущей калибровки; сам факт возвращения кандидатов не означает ошибочный ответ.

Это проверка поиска по локальному снимку базы, а не фактической правильности
ответов. Уточняющие вопросы имеют ручные самостоятельные формулировки, поэтому
качество переписывания истории здесь не измеряется. Поиск dense выполняется
точным cosine по `runtime/points_cache.jsonl`, без Qdrant: его сетевые задержки
и поведение ANN в эти цифры не входят. Старый кеш не содержит идентификатор
эмбеддера: стенд перепроверяет три вектора документов текущей моделью с исходным
префиксом и требует cosine не ниже 0.995. При несовпадении используйте
`--reembed-corpus`: векторы пересчитаются в памяти, исходный кеш останется целым.
Наличие NLTK stopwords
фиксируется в отчёте и должно совпадать у сравниваемых прогонов.

Вопросы разделены по семействам на `calibration` и `holdout`. Порог routing
можно подбирать только на calibration, затем проверять на holdout; варианты
вопросов внутри семейства не разделяются. Пока пороги не подобраны, автоматический
ранний выход по confidence не включён. Production top-k и текущая политика
`FAST_PATH_RERANK_POLICY` этим стендом не изменяются.

После полного сравнения можно проверить экспериментальный BM25 early-exit:

```powershell
uv run python -m eval.analyze_routing runtime/retrieval-benchmark/runs.jsonl --fallback hybrid
```

Скрипт подбирает сочетание BM25-score, отрыва первого результата и покрытия
терминов на calibration, затем отдельно показывает ошибки на holdout. Это
симуляция задержки последовательного каскада; она не включает LLM и не меняет
настройки приложения. Даже отсутствие ошибок на таком небольшом наборе не
делает score вероятностью правильного ответа.

Пересобрать набор из локальных старых eval-файлов и дополнительных вопросов:

```powershell
uv run python -m eval.build_dataset
```

Сгенерированный `eval/golden.jsonl` включается в Git, поэтому
для обычного запуска исходные локальные eval-файлы не нужны.

### Первый эксперимент: 11 октября 2026

На локальном корпусе из 319 чанков выполнен один проход по 139 вопросам,
из них 125 с ответом и 92 с разметкой конкретных разделов. CPU, 4 потока,
8 кандидатов, top-5, без metadata boosts и без NLTK stopwords.

| Режим | Все нужные разделы в top-5 (92 вопроса) | p50 поиска | p95 поиска |
|---|---:|---:|---:|
| BM25 | 73,9% | 3 мс | 5 мс |
| BGE-M3 | 90,2% | 499 мс | 707 мс |
| BM25 + BGE-M3 + RRF | 92,4% | 510 мс | 732 мс |

Это пилотный retrieval-эксперимент, не оценка правильности ответов LLM.
Часть вопросов создана по шаблонам; преимущество гибрида над dense составляет
два вопроса и требует проверки на реальных обращениях. Использовано изолированное
окружение с Torch 2.8.0+cpu и Sentence Transformers 5.1.2, а не весь старый
`uv.lock`; точные версии записаны в отчёте. Латентность зависит от окружения.

Обязательный rerank исключён из полного прогона после проверки задержки.
Для 22 запросов с 8 кандидатами и лимитом 256 токенов получены p50 14,34 с и
p95 19,52 с. Полный набор с rerank не завершён, его качество не сопоставляется
с таблицей выше. Более тяжёлый вариант (20 кандидатов, 512 токенов) также
прерван; частичные измерения сохранены отдельно с `complete: false`.

Гейт BM25 (score >= 4.778, относительный отрыв >= 0.3, покрытие терминов >= 0.4)
подобран только на calibration: 29 ранних выходов без наблюдаемых ошибок.
На holdout он дал 11 ранних выходов, из которых 2 потеряли нужный раздел,
найденный гибридом. Гейт **не включать** по этим результатам. В holdout лишь
один вопрос без ответа, поэтому качество отказов на этой разбивке не установлено.

Выбор для следующего этапа: гибрид без обязательного rerank и без такого
раннего выхода. Для сравнений программ все три метода нашли нужные разделы
только в 3 из 8 случаев: нужен отдельный эксперимент с разбиением запроса
и поиском по каждой программе. Настройки старого чата пока не переключены.

Подробные локальные результаты:

- `runtime/retrieval-baseline/summary.json` и `runs.jsonl`: полный проход трёх режимов.
- `runtime/retrieval-baseline/routing-hybrid.json`: калибровка и holdout для гейта.
- `runtime/retrieval-compact/summary.json`: частичный опыт с компактным rerank.
- `runtime/retrieval-full/summary.json`: частичный опыт с 20 кандидатами.

### Структурированные карточки и сравнения программ

`backend/app/rag/structured.py` содержит экспериментальную подготовку карточек и разбиение
вопроса по явно названным программам. Исходные границы чанков, разделы и полный
текст сохраняются: улучшение метрики нельзя получить простым склеиванием всех
разделов документа. В BGE передаются читаемые поля «Документ / Программа / Код /
Раздел / Период действия», значения таблицы «Поле / Значение» и исходный текст.
Ссылки из явно обозначенных строк источника хранятся в payload. Отсутствующие
даты не придумываются, `updated_at` не используется как период действия.

Типизированное извлечение пока ограничено однозначными значениями «Пороговый
балл на грант» и «Срок обучения»; код программы остаётся строкой. Сложные условия,
стоимость и остальные значения сохраняются исходным текстом. Числовая фильтрация
в этом эксперименте не включена; для неё нужна отдельная проверка единиц,
условий и применимости на конкретный год.

```powershell
uv run python -m eval.structured_compare --repeats 1 --candidates 8
uv run python -m eval.report_structured
```

Нужен локальный снимок BGE-M3 в `tmp/models`. Отчёты и новые векторы пишутся
отдельно в `runtime/structured-experiment/`; исходный индекс не перезаписывается.
Кеш новых векторов привязан к содержимому карточек и пути ревизии модели.

Стенд сравнивает четыре режима на одном наборе вопросов:

- `hybrid`: исходный BM25 + BGE + RRF.
- `hybrid_fanout`: тот же корпус, отдельный запрос на каждую явно названную программу.
- `cards`: новые карточки и их векторы, один запрос.
- `cards_fanout`: карточки вместе с отдельными запросами.

В fan-out из формулировки убираются названия других программ, сохраняется тема,
добавляется имя и код текущей программы. Отбор идёт по очереди из каждой группы
до общего top-5. Запросы последовательные, время каждого эмбеддинга включено.
Программа определяется по тексту вопроса, не по его категории или эталонным
источникам. Для одного упоминания сохраняется прежний способ поиска.

`report_structured` экспортирует карточки без векторов (`evidence-cards.jsonl`),
пример сгруппированного контекста (`example-context.md`) и список улучшений и
регрессий по каждому вопросу (`paired-changes.json`). Несколько нужных разделов
одного документа могут присутствовать вместе. Этот этап не проверяет ответы
LLM, применимость исключений или полноту общих правил; live-маршрут чата не меняется.

Результат полного прогона 11 октября 2026: 139 вопросов × 4 режима = 556
измерений, один повтор, CPU / 4 потока / 8 кандидатов / top-5. Совместимость
исходных векторов повторно проверена: cosine = 1.0 на всех трёх образцах.

| Режим | Все нужные разделы (92 вопроса) | Разделы обеих программ (8 сравнений) | p50 / p95 поиска |
|---|---:|---:|---:|
| Исходный гибрид | 85/92 — 92,4% | 3/8 | 159 / 215 мс |
| Исходный гибрид + отдельные запросы | 84/92 — 91,3% | 2/8 | 156 / 386 мс |
| Карточки | 84/92 — 91,3% | 3/8 | 159 / 214 мс |
| Карточки + отдельные запросы | 86/92 — 93,5% | 5/8 | 159 / 403 мс |

Для самих сравнений медиана выросла с 215 до 418 мс у карточек с отдельными
запросами. Все четыре варианта измерены вперемешку в одном запуске. Абсолютные
времена заметно отличаются от первого эксперимента; это не основание приписывать
трёхкратное ускорение карточкам. Сравнивать задержки следует внутри этого запуска.

Комбинация карточек с раздельным поиском даёт четыре улучшения и три регрессии
относительно исходного гибрида — чистый выигрыш лишь один вопрос. Регрессии:
`followup_0`, `program_6B03201_semantic`, `bda_subjects_001`. На известной разбивке
holdout: 20/20 против 19/20 размеченных вопросов, но все восемь сравнений находятся
в calibration. Этот небольшой ранее просмотренный набор не является независимой
проверкой обобщения; вариант не выбран для автоматического включения в чат.

Отдельные запросы находят оба файла во всех 8 сравнениях, но нужные разделы могут
не попасть в top-5: остаются «Краткое описание» и «Основная информация» вместо
навыков/дисциплин. Следующая проверяемая гипотеза — отбор разделов по теме вопроса
при сохранении покрытия каждой программы. Просто присутствие обоих документов
не означает достаточного контекста для ответа.

Экспортированы 319 карточек, 169 с явными URL источников, 32 типизированных факта.
Первичное кодирование карточек заняло около 13,5 минуты и не входит в задержку
поиска. Полные результаты: `runtime/structured-experiment/summary.json`,
`runs.jsonl`, `paired-changes.json`, `evidence-cards.jsonl`, `example-context.md`.

### Отбор разделов по теме вопроса

`requested_sections` и `prefer_sections` в `backend/app/rag/structured.py` распознают явные
вопросы о навыках, дисциплинах и карьере. Подходящие `section_type` профиля
программы поднимаются выше среди тех же 8 найденных кандидатов. Это стабильная
перестановка, без удаления остальных кандидатов и без фильтрации всего корпуса.
Неизвестная тема или отсутствие подходящих разделов сохраняют прежний порядок.
При сравнении программ отбор выполняется отдельно для каждой, затем применяется
общий лимит top-5. Новых моделей и cross-encoder rerank здесь нет.

```powershell
uv run python -m eval.section_compare
```

Скрипт использует готовые векторы предыдущего эксперимента и сохраняет результаты
в `runtime/section-experiment/`. Запуск 11 октября 2026: 695 измерений (139 вопросов
× 5 вариантов), CPU, 4 потока, один повтор; порядок режимов перемешан.

| Вариант | Все нужные разделы | Сравнения программ | p50 поиска |
|---|---:|---:|---:|
| Исходный гибрид | 85/92 | 3/8 | 153 мс |
| Гибрид + отдельные запросы | 84/92 | 2/8 | 153 мс |
| Гибрид + отдельные запросы + отбор разделов | **91/92** | **8/8** | 154 мс |
| Карточки + отдельные запросы | 86/92 | 5/8 | 154 мс |
| Карточки + отдельные запросы + отбор разделов | **91/92** | **8/8** | 153 мс |

Отбор сам по себе занимает в среднем около 0,044 мс. Для сравнений медиана всей
цепочки на исходных векторах — 402 мс: она включает два последовательных поиска
и эмбеддинги обоих запросов. Переэмбеддинг карточек не дал преимущества по полноте
после добавления отбора разделов. Предпочтительный кандидат для дальнейшего
внедрения — исходные векторы + отдельные запросы + отбор разделов.

Против исходного гибрида: 6 улучшений, 0 регрессий по размеченным разделам.
Единственный промах — `smart_skills_001`: найдены разделы дисциплин, а разметка
требует раздел навыков. Это не проверка фактической ошибочности ответа LLM.
Все восемь сравнений шаблонные и находятся в calibration; holdout остаётся
19/20. Необходима проверка на независимых формулировках перед широкими выводами.
Правила не читают эталонные ответы и не подбирались после этого прогона.

Live-маршрут чата этим экспериментом не меняется. Ссылки на источники остаются
служебными данными; их показ пользователю не добавляется.
